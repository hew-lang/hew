## The root, restated

`callee_returns_fresh_owner(callee, &HashMap<ItemId, bool>)` read the COARSE
freshness fixpoint. That fixpoint answers a narrower question (may a return
alias a by-value parameter) and cannot see an extern at all: a declared
`extern "C"` fn is body-less, so the walk's `unwrap_or(true)` cross-ABI fallback
classifies an un-audited host as a fresh-owner producer, and one Hew frame
around it inherits a `true` row.

Round 2 conjoined `!launders_opaque_extern(id)` at ONE call site. The map was
still a parameter of the shared helper, so every other consumer kept the
un-vetoed answer:

* **Finding 1** — `ownership.rs:371-372`, the composite temp-arg mint. Its
  extern veto matched a direct extern by NAME; a Hew wrapper is not a direct
  extern, so it fell through to the coarse verdict. `borrow(wrap())` minted a
  caller drop over a host handle.
* **Finding 2** — `ownership.rs:2756`, `expr_is_materialized_owner`. The same
  wrapper read as a materialized owner and routed to `hew_vec_push_owned_move`;
  the Vec's teardown then released the host handle.

## The fix: one authority, unbypassable by construction

`hew-mir/src/return_provenance.rs` gains

```rust
pub struct FreshOwnerVerdicts {
    rows: HashMap<hew_hir::ItemId, bool>,   // coarse ∧ ¬laundering
    opaque_extern_names: HashSet<String>,   // declared, un-audited extern names
}
```

Four properties make the tainted verdict impossible to bypass. I am claiming
these as *structural*, not as *review discipline*:

1. **The rows are private.** No consumer can reach the un-conjoined coarse
   verdict through the type, because there is no accessor that returns it.
2. **There is exactly one constructor, and it is crate-private.**
   `FreshOwnerVerdicts::build` is called from exactly one place,
   `build_call_scrutinee_provenance`. It conjoins each coarse row with
   `compute_fn_return_launders_opaque_extern`, then UNIONS the taint set in as
   explicit `false` rows — so a laundering id the coarse fixpoint never keyed
   lands as `false` rather than falling through the `unwrap_or(true)` fallback.
3. **The coarse map is no longer in scope for anyone else.** In `lower_module`
   it is a local, `coarse_fn_returns_fresh`, whose only use is the argument to
   `build_call_scrutinee_provenance`. The `Builder` field that used to carry it
   (`funcupdate_fn_returns_fresh`) is gone; the field is now
   `fresh_owner_verdicts: Rc<FreshOwnerVerdicts>`.
4. **The consumer signatures are type-incompatible with a map.**
   `callee_returns_fresh_owner`, `callee_returns_analyzed_fresh_owner`,
   `expr_is_materialized_owner`, `compute_funcupdate_base_provenance` and
   `BaseOwnerResolver` all take `&FreshOwnerVerdicts`. A future consumer that
   tries to pass a `HashMap<ItemId, bool>` does not compile. A future consumer
   that constructs its own authority cannot: `build` is private to the crate and
   the only public way in is `CallScrutineeProvenance::fresh_owner_verdicts`,
   which is already conjoined.

The reviewer's instruction offered two shapes — make the coarse map unreachable,
or make `callee_returns_fresh_owner` consult the taint. This does both, and the
second only because it is now impossible to do otherwise: the taint is not a
lookup the helper performs, it is already folded into the row it reads.

### Two vetoes, because one key space is not enough

* **Wrapper laundering is id-keyed.** Rows come from the transitive
  `compute_fn_return_launders_opaque_extern` fixpoint over the audited
  `ExternContractTable`. Wrapper, wrapper-of-wrapper, generic wrapper (analyzed
  at its origin `ItemId`, which is what a monomorphisation's callee resolves to)
  and recursive-looking wrapper all read `false`.
* **A direct extern must be name-keyed.** An extern call site's
  `ResolvedRef::Item` carries a PLACEHOLDER id, never the declaration's, so an
  id lookup both misses the extern and collides with the module-fn summary id
  space. The declared un-audited extern NAMES therefore ride in the same object
  and are vetoed first, inside `callee_returns_fresh_owner` /
  `callee_returns_analyzed_fresh_owner`, before any row is consulted.

Carrying the name veto in the authority — rather than leaving it open-coded at
one call site — is what closed Finding 3 for free.

### Type-agnostic, as required

Neither the laundering fixpoint nor the extern contract table filters on
`string`. `compute_fn_return_launders_opaque_extern` walks return provenance
structurally; `ExternContractTable::extern_return_is_audited_fresh_owner` keys
on the declared symbol. A record, a tuple, an enum payload and a `Vec` element
are covered identically. The new regressions exercise a `record Holder` return
specifically so this is measured and not asserted.

### Two fallbacks, chosen by blast radius

* `item_returns_fresh_owner` keeps the coarse `unwrap_or(true)` for an ABSENT
  row — the cross-ABI owned-return contract that covers aggregate constructors
  and compiler-minted runtime primitives. None of those are declared externs and
  none can be tainted, so the fallback cannot launder.
* `item_returns_analyzed_fresh_owner` drops the fallback: `Some(&true)` only.

A consumer whose worst case is a double release uses the strict one; a consumer
whose worst case is a missed move/clone optimisation uses the former.

## Finding 3, unreported: a direct extern into a `Vec`

`expr_is_materialized_owner` had NO extern veto at all — not even the by-name
one Finding 1's site had. So `v.push(host_record())`, calling the opaque extern
DIRECTLY with no wrapper, also moved a foreign handle into the Vec. The review
found the wrapper case; the bare case was worse and adjacent. Folding the name
veto into the authority closed it in the same edit, and
`direct_extern_result_pushed_into_a_vec_stays_copy_in` pins it.

### `hew-cli/tests/extern_ownership_double_release_e2e.rs` — two native cases

The MIR assertions say the mint is gone; these say the host's handle is never
released. Same exact-count release counter as round 2 (`HeaderAware` ABI, host
mints genuine header-aware handles over the pinned 16-byte
`{ magic: u64, rc: u32, _reserved: u32 }` layout with `rc` biased by 1 000 000,
so nothing can be freed under the probe and every compiler release reads as an
exact decrement).

The probe class had to change for the Vec case. `Vec<string>::push` lowers to
`hew_vec_push_str`, NOT the owned/move seam — the string spy literally cannot
observe Finding 2. So the fixture pushes a `record Holder { label: string }`
whose single field is a header-aware handle, returned by value from the host as
a `repr(C)` struct.

| test | shape | previous HEAD | new HEAD |
| --- | --- | --- | --- |
| `a_vec_push_of_a_wrapped_extern_record_sees_no_caller_release` | `v.push(wrapHolder())` × 8 | `releases=8` | **0** |
| `a_wrapped_extern_record_in_a_borrowing_argument_sees_no_caller_release` | `borrowHolder(wrapHolder())` × 8 | `releases=8` | **0** |

Both report `after_host_release=1` — the counter's positive control, one real
host-issued `hew_string_drop` reading as exactly one decrement, run last. The
zeros are measurements, not a blind probe. The same net-decrement limitation I
recorded in round 2 still applies and I am not restating it as a proof.

Post-fix zero is not an accident of the fix removing work: COPY-IN
`hew_vec_push_owned` deep-clones, RETAINING the label into the slot, so the Vec
teardown releases that retained share and nets to zero against the host's own
reference. The handle stays valid, which is the point.
