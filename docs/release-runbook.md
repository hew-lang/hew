# Hew Release Runbook

How a Hew release is prepared, tagged and shipped. A pushed `v*` tag is the
only trigger: `.github/workflows/release.yml` builds every artefact once and
publishes all of them, pausing only for environment approvals.

For outstanding compiler/client and package qualification, see the
[release and ecosystem readiness handoff](release-readiness.md).

## What happens on a `v*` tag

```
validate ─► build ─────────────► package and prove ─► release-assets ─► github-release ─► publish jobs
```

1. **validate** checks that the tag points at the run's commit and that
   `scripts/release-identity.sh` agrees (Cargo.toml, `hew-sandbox-vm`,
   `docs/syntax-data.json`, `docs/releases/<tag>.md`), then runs
   `make release-checks` (dependency policy, notices, installer ordering).
2. **build** produces, in parallel: the portable WASI libraries, the
   cross-built FreeBSD and Windows libraries, the five current platform archives
   (Linux x86_64/aarch64, macOS arm64 signed and notarized, Windows
   x86_64, FreeBSD x86_64), and the two npm tarballs
   (`@hew-lang/wasm` from `hew-wasm`, `@hew-lang/sandbox-vm`).
3. **package and prove**: Linux distro packages with install smoke (final
   releases only; rpm and Arch versions cannot carry `-rcN`), the Docker image
   assembled from each Linux archive and proved by the clean-room installation
   test, and the docs site generated by the packaged compiler.
4. **release-assets** requires the complete set and writes
   `hew-v<version>-checksums.txt` over it.
5. **github-release** creates a draft, uploads the set, records a build
   provenance attestation for every asset, then publishes the release
   (prerelease for `-rcN`). No approval: the signed tag on the protected
   `release-tags` ruleset is the decision to release.
6. **Publish jobs** run in parallel from the same artefacts:

   | Job                       | Destination                                                        |
   | ------------------------- | ------------------------------------------------------------------ |
   | `publish-npm`             | npmjs `@hew-lang/{wasm,sandbox-vm}`, provenance                    |
   | `publish-github-packages` | GitHub Packages mirror of the same tarballs                        |
   | `publish-ghcr`            | `ghcr.io/hew-lang/hew:<version>` (+ `latest` for finals), attested |
   | `publish-homebrew`        | waits for `hew-lang/homebrew-hew` and verifies formula sources     |
   | `publish-docs`            | docs.hew.sh (Cloudflare Pages `hew-docs`)                          |

   Every publish job names the one `release` environment. GitHub's
   **Review deployments** dialog approves by environment, so a single click
   releases all five waiting jobs. Prereleases publish npm on dist-tag `next`
   and never move Docker `latest`; finals take `latest` on both.

npm and GitHub Packages verify the complete published tarball against the
source-stamped producer archive. GHCR verifies the image index and both
architecture digests. Conflicting content or an unreadable destination fails
the job. Homebrew reuses a completed update or waits for an existing active
run before dispatching a new one. It checks formula versions, source URLs and
checksums against the release artefacts. A published
GitHub Release is never modified, so **Re-run failed jobs** on the
tag's run is the recovery path for any failure. Dispatching `release.yml` from
the tag ref with `dry_run` cleared starts a fresh run of the same tag. A
dispatch from a branch, and every push to `release/**`, is a dry run: it builds
and proves everything and publishes nothing; a dispatch from a branch with
`dry_run` cleared is refused.

Release artefacts on the GitHub Release:

- `hew-v<version>-<platform>.tar.gz` / `.zip`: the five current toolchain archives
- `hew-v<version>-wasm32-wasip1-libs.tar.gz`: the WASI runtime and standard
  library (`libhew_runtime.a`, `libhew_std.a`) that every archive also carries
- `hew-lang-wasm-<version>.tgz`, `hew-lang-sandbox-vm-<version>.tgz`: the
  exact npm tarballs published to both registries
- Linux `.deb`, `.rpm`, `.pkg.tar.zst` (final releases)
- `hew-v<version>-checksums.txt`, covering all of the above; verify an asset's
  provenance with `gh attestation verify <file> --repo hew-lang/hew`

## One-time setup

One protected environment, `release`, gates every external destination. An
environment a workflow names but nobody configured is created unprotected and
would publish without a click, so create it with a required reviewer and a
`v*` tag policy (`bash npm-user-steps.sh env` does the same):

```bash
gh api -X PUT "repos/hew-lang/hew/environments/release" --input - <<JSON
{"reviewers":[{"type":"User","id":37180}],"prevent_self_review":false,
 "deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}
JSON
gh api -X POST "repos/hew-lang/hew/environments/release/deployment-branch-policies" \
  -f name='v*' -f type=tag
```

Repository secrets: `APPLE_CERTIFICATE_P12`, `APPLE_CERTIFICATE_PASSWORD`,
`APPLE_API_KEY_P8`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER_ID` (macOS signing
and notarization), `HOMEBREW_TAP_TOKEN` (actions:write on
`hew-lang/homebrew-hew`), `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
npm needs no token: `@hew-lang/wasm` and `@hew-lang/sandbox-vm` each trust
publisher `hew-lang/hew`, workflow file `release.yml`, environment `release`.
Until that binding names `release.yml`, `publish-npm` fails authentication;
re-point the trust (`npm trust revoke`, then `npm trust github ... --file
release.yml --env release`) and re-run the failed job.

## Downstream repositories

Each sibling repository releases from its own `v*` tag and consumes the
published Hew release; nothing here pushes into them.

- **vscode-hew**: bump `package.json` and pin the new archives' hashes in
  `hew-release.sha256`, then tag. Its `release.yml` bundles `hew` and
  `std/` from the pinned archives, starts the language server with `hew lsp`,
  and publishes to the Marketplace behind its
  `vs-marketplace` environment (Entra ID OIDC, no PAT).
- **tree-sitter-hew**: tag after a grammar change; `publish.yml` publishes
  `@hew-lang/tree-sitter-hew` to npmjs by trusted publishing behind its `npm`
  environment.
- **homebrew-hew**: driven by `publish-homebrew` above; `update-formula.yml`
  downloads the release archives and commits the formulae.
- **playground-client and playground-sandbox**: publish their package archives
  as immutable GitHub Release assets, with checksum sidecars. The sandbox
  wrapper pins its compiler and VM dependencies; publish a matching wrapper
  after the new engine packages are available, before updating browser consumers.
  Verify the actual published archives against their checksums.
- **hew.sh and hew.run**: pin `@hew-lang/wasm` and `@hew-lang/sandbox-vm` to the
  same published engine version from npmjs. Pin the client and sandbox wrapper
  dependencies to their public GitHub Release archive URLs and regenerate the
  lockfile from those published bytes. Remove obsolete GitHub Packages scope
  routing from the consumer. Prove a fresh installation with empty user/global
  npm configuration and no package-registry credentials, then run the consumer's
  build and browser checks. Keep the prior released pins until the complete
  replacement dependency graph is published and verified.
- **playground**: the server consumes the published packages and release assets
  on its own build and deployment pipeline. Browser package updates do not
  require a new server image to be published by the compiler release workflow.

## Platform policy

Linux x86_64 and aarch64 are the primary platforms. macOS on Apple silicon is
secondary. Windows and FreeBSD remain supported; Intel macOS is retired.

A major regression that prevents the compiler/runtime from building or running,
or prevents a basic Hew program from compiling and executing, blocks a release
on any supported platform. Establish whether the failure is a product regression,
a runner/toolchain problem or a defective test before assigning that severity.

For patch releases, require successful Linux qualification and the relevant
safety, integration and packaging checks. Assess other platform failures against
their actual impact, the Linux correctness/performance benefits and the cost of
resolving platform-specific friction. Windows and FreeBSD test failures may be
backlogged rather than delay a substantive Linux patch. Apply the same impact
assessment to secondary macOS coverage. This does not permit a known major
build/run regression to be deferred.

Record each accepted nonblocking failure with the tested revision, affected
behaviour, evidence, owner and intended resolution in another patch or before
the next minor release. Preserve failed and pending results as such; accepting a
release does not turn them green. Continue useful running checks without
restarting successful suites. Review the platform backlog before a minor release.

For the 0.6 series, standalone WASI and non-browser WebAssembly builds are
non-gating. Keep the compiler/VM checks necessary for browser development and
actual browser sandbox execution. Matching unsupported cases are not parity.
Optional target or harness work must not displace the native Linux outcome.

## Phase 1 — Assemble the candidate

```bash
# Ensure you're on a clean, up-to-date main
git checkout main && git pull --ff-only

# Verify the candidate commit
git log --oneline -5  # confirm expected HEAD
```

## Breaking change discipline (pre-1.0)

**Recognizing breaking public-API changes:**

- Adding a variant to a `pub enum` without `#[non_exhaustive]` breaks exhaustive-match callers.
- Changing the signature of a `pub fn` (parameter count, order, type, or return type).
- Removing or renaming an exported `pub` item.
- Narrowing the visibility of a previously public item.

**Handling breaks (pre-1.0):**

1. **In the PR:** describe the changed behaviour and migration. Use `#[non_exhaustive]` when an enum is designed for future extension; adding it to an existing exhaustive enum is itself a change that needs migration instructions.
2. **In-tree callers:** update all tests, examples, probes, and docs in the same PR — never carry forward compatibility aliases. The break is immediate and clean.
3. **CHANGELOG entry:** in the `[Unreleased]` section, add a `### Changed` entry listing the affected module paths, the old shape, and the new shape with a one-line migration note. Example:

   ```
   ### Changed

   - **String iteration:** replace `text.chars()` with `text.iter()`.
     The iterator still yields `char` values.
   ```

4. **Version:** approved language and stdlib changes may ship in the evolving 0.6.x series. Identify the first supporting compiler version and document affected versions and exact migration steps. See the [specification's version model](specs/HEW-SPEC-2026.md) and [versioning guidance](internal/versioning.md).

**Rationale:** pre-1.0, breaking changes allow rapid stdlib refinement without long deprecation cycles. All in-tree code must be updated in the same PR so the break is visible at a glance. `#[non_exhaustive]` protects downstream code from silent miscompilation.

## Phase 2 — Establish the release identity

> **Prerequisite:** Any required version bump must update `Cargo.toml`'s
> workspace version, every lockfile, `docs/syntax-data.json`, the dated
> changelog record, and the exact `docs/releases/vX.Y.Z.md` file together.
> Tagging a commit where any one of those identities differs produces a split
> release record.

```bash
# Set the intended version in the root [workspace.package], if needed.
$EDITOR Cargo.toml

# Keep a fresh [Unreleased] heading and stamp its completed entries under the
# dated [X.Y.Z] heading. Create docs/releases/vX.Y.Z.md at the same time.
$EDITOR CHANGELOG.md
$EDITOR docs/releases/vX.Y.Z.md

# Update and verify every committed lockfile through Cargo.
cargo check --workspace
cargo check --workspace --locked
cargo update --manifest-path hew-parser/fuzz/Cargo.toml \
  -p hew-parser --precise X.Y.Z --offline

# Confirm the identity that all later commands derive.
release_tag="$(scripts/release-identity.sh)"

git add Cargo.toml Cargo.lock hew-parser/fuzz/Cargo.lock docs/syntax-data.json \
  CHANGELOG.md "docs/releases/${release_tag}.md"
git commit -m "chore(release): prepare ${release_tag}"
```

`scripts/release-identity.sh` prints the tag only when Cargo.toml,
`hew-sandbox-vm/package.json`, `docs/syntax-data.json` and
`docs/releases/<tag>.md` agree.

## Phase 3 — Push release branch (release gate and release dry run)

```bash
set -euo pipefail
release_tag="$(scripts/release-identity.sh)"
test "$(git status --porcelain)" = ""
release_sha="$(git rev-parse HEAD)"
git checkout -b "release/${release_tag}"
git push origin "release/${release_tag}"
printf 'Record candidate %s: %s\n' "$release_tag" "$release_sha"
```

Record the full `release_sha` with the qualification evidence before merging.
If the candidate changes, record its new SHA and qualify that candidate again.

This triggers two workflows. `.github/workflows/release.yml` runs the
complete release DAG as a dry run (every archive, package, image, npm tarball
and the docs site, publishing nothing), so tag-time packaging fails here
rather than on the tag. `.github/workflows/release-gate.yml` checks the
release identity and `make release-checks`, then runs:

| Platform       | Build scope                    | Test scope                                                   |
| -------------- | ------------------------------ | ------------------------------------------------------------ |
| Linux x86_64   | hew-cli, hew-lib, WASM runtime | Rust workspace, codegen E2E (native + WASM)                  |
| Linux aarch64  | hew-cli, hew-lib, WASM runtime | Rust workspace, codegen E2E (native + WASM)                  |
| macOS arm64    | hew-cli, hew-lib               | Rust workspace, codegen E2E (native)                         |
| Windows x86_64 | hew-cli, hew-lib               | Rust workspace + C-ABI + executable release-library consumer |
| FreeBSD x86_64 | hew-cli, hew-lib               | Rust workspace + C-ABI + executable release-library consumer |

Each toolchain carries one executable. Language-server and Observe entry points
are `hew lsp` and `hew observe`; neither needs a sibling executable.

Apply the platform policy above to every result on the recorded `release_sha`.
Require successful Linux qualification, executed `gate-sanitizers` and the
relevant `release.yml` packaging proof. Record any accepted secondary/optional
platform failure and its follow-up; a pending job is not a pass. Rust workspace
jobs use `make test-strict`; their green result means an all-pass result.
Report known failures separately from passing tests.

If Windows needs a focused retry after a workflow correction, use the
updated gate with the original candidate's full commit SHA:

```bash
gh workflow run release-gate.yml --ref main \
  -f source_sha="$release_sha" \
  -f platforms=windows-x86_64
```

This runs candidate validation, identity and dependency checks, then Windows.
Use `platforms=macos-aarch64` for a focused Apple silicon run. A green partial
run supplies only the selected platform results.
For each contributing run, record its URL and the qualification summary's
source SHA, workflow SHA and platform selection. Except for the scoped
reuse described below, every source SHA must match the recorded
`release_sha`. Review workflow corrections for changes to the required checks.
Combine successful scoped runs with applicable results from the full gate.
Missing, skipped, cancelled or failed primary checks still need successful
evidence. Other platform results follow the recorded impact assessment above.
Requalify affected contracts on the changed candidate, and run a new
release dry run when implementation, dependency, build or packaging inputs change.

Completed qualification may be retained for unchanged contracts. Record both
commits, review their complete diff and explain why each retained platform or
component result still applies. Identify results by the commit actually tested.
A platform-specific change requires fresh qualification of that platform; shared
compiler, runtime, dependency or harness changes require every affected check.
When the impact cannot be bounded confidently, run the full qualification again.

Run corrected tests and their direct consumers on relevant platforms, including
any platform that failed. An isolated fixture correction can use the qualified
compiler/runtime pair when production inputs are unchanged. Preserve behavioural
assertions and resolve all failures; pending, skipped and failed jobs cannot be
reused as successful evidence. Required protected CI must still pass on the final
candidate. Do not describe reused results as an exact-final-commit matrix.

The workflow's native job checks and run metadata identify the dispatched
workflow revision. Candidate-bound JUnit checks and the qualification summary
identify the tested source. Leaving both inputs at their defaults runs the full
gate on the workflow commit.

## Release dependencies and notices

`make release-checks` (cargo-deny 0.19.6, cargo-about 0.9.0) checks allowed
licences, known security advisories, permitted dependency sources, generated
third-party notices and installer version ordering. The release gate and the
tag workflow's validate job both run it through
`.github/actions/setup-release-checks`.

Duplicate dependency versions are permitted and are not reported. Other
policy warnings fail validation: update the dependency or document a specific
exception in `deny.toml`. When the dependency graph changes, run `make licenses`
and commit `Cargo.lock` and `THIRD-PARTY-LICENSES` together. Generation uses the
locked graph and fails if a licence cannot be resolved.

Release validation runs the dependency-policy part (`make dependency-policy`).
`make pre-release` runs the full set before platform validation.

## Phase 4 — Local cross-platform validation (optional but recommended)

For full cross-platform hardware validation beyond CI runners:

```bash
# Linux only (fast, local)
make pre-release PLATFORMS="linux"

# Linux x86_64 + optional Linux aarch64 remote validation
make pre-release PLATFORMS="linux linux-aarch64"

# All platforms (requires .env.pre-release with SSH host config)
make pre-release
```

If your only local arm64 hardware is Debian bookworm (for example pirea51),
do not treat LLVM 22 apt failures there as a repo regression:
`apt.llvm.org/bookworm` arm64 may not publish the LLVM 22 development packages
that `llvm-sys` needs (`llvm-22-dev`, `clang-22`, or `lld-22`). The
authoritative local/CI-compatible path is Ubuntu 24.04 arm64
(`ubuntu-24.04-arm` in CI, or an Ubuntu 24.04 arm VM/container locally).

Requires `.env.pre-release` in the repo root (gitignored):

```bash
MACOS_HOST=my-mac.local
# Optional when LLVM 22 is outside the standard Homebrew locations:
HEW_MACOS_LLVM_PREFIX=/opt/homebrew/opt/llvm@22
LINUX_AARCH64_HOST=user@ubuntu-24-arm-host
FREEBSD_HOST=user@freebsd-host
WINDOWS_HOST=user@windows-host
# Required for Windows validation; build it with `make windows-release-candidate`
# (archives the committed HEAD tree — Cargo.toml/Cargo.lock/crate sources —
# since scripts/windows-release-build.ps1 runs `cargo build` on the Windows
# host itself; it does not consume precompiled artifacts).
HEW_WINDOWS_CANDIDATE_ARCHIVE=/absolute/path/to/target/hew-windows-candidate.tar.gz
```

Build the candidate archive from the repo root before running Windows
validation:

```bash
make windows-release-candidate
export HEW_WINDOWS_CANDIDATE_ARCHIVE="$(pwd)/target/hew-windows-candidate.tar.gz"
```

The Windows host must also have a populated Cargo cache for the workspace's
locked dependencies: `windows-release-build.ps1` runs
`cargo fetch --locked --offline` before building and fails validation outright
if that cache is missing, so run `cargo fetch --locked` (online) on the
Windows host at least once beforehand.

Windows hosts also need Visual Studio C++ Build Tools with a Windows SDK and a
one-time LLVM 22 install that matches the tag release workflow: install into
`C:\llvm-22`, verify `vswhere.exe` can find the x64 C++ tools, and verify
`C:\llvm-22\bin\clang.exe` exists before running `make pre-release`. See
[`docs/cross-platform-build-guide.md`](cross-platform-build-guide.md#windows)
for the exact bootstrap command sequence. The validator defaults to
`LLVM_PREFIX=C:\llvm-22`; it imports `VsDevCmd.bat` for the SDK/CRT environment
before prepending `C:\llvm-22\bin` to `PATH`. Override with
`HEW_WINDOWS_LLVM_PREFIX`, `HEW_WINDOWS_CC`, and `HEW_WINDOWS_CXX` if that host
uses a different compiler driver. Windows validation consumes the configured
candidate archive without rebuilding it locally. It also runs Cargo offline, so
the Windows host must have a populated Cargo cache for the locked dependencies.

The macOS validator requires an LLVM 22 root. It first honors
`HEW_MACOS_LLVM_PREFIX` (or `MACOS_LLVM_PREFIX` in `.env.pre-release`), then
uses `brew --prefix llvm@22` when `brew` is available, and finally probes
`/opt/homebrew/opt/llvm@22` and `/usr/local/opt/llvm@22` directly. Each
candidate is accepted only when its `bin/llvm-config --version` reports major
version 22; an absent or different version fails validation before building.

What `make pre-release` does:

1. `make release-checks` — dependency policy, notices and installer ordering
2. `scripts/pre-release-validate.sh` — per-platform:
   - Build all release artifacts
   - Verify binaries exist and run (`--version`)
   - Smoke test: compile and execute a .hew program
   - Linux: verify no dynamic LLVM deps (`ldd` check)
   - Linux aarch64 (optional): stage the local candidate in a fresh remote
     temporary directory, then build on Ubuntu 24.04 arm64 with LLVM 22
     provisioned from `apt.llvm.org/noble`
   - macOS and FreeBSD: stage the local working-tree candidate in a fresh
     remote temporary directory. Windows stages the configured candidate
     archive in its own fresh remote directory. Existing host checkouts are
     never reset, updated, or used as a fallback.
   - Every requested remote platform fails closed when its host is absent or
     unreachable. Narrow `PLATFORMS` explicitly when omitting a host.
   - Windows: require `LLVM_PREFIX`, then compile+run a smoke program so
     validation cannot silently pass a frontend-only `hew.exe`

For a local macOS clean-room check of the Homebrew/release binary shape:

```bash
cargo build -p hew-cli --release
scripts/verify-macos-binary.sh target/release/hew
cat > hew-smoke.hew <<'EOF'
fn main() { println("Hello from Hew!"); }
EOF
./target/release/hew version
./target/release/hew check hew-smoke.hew
rm -f hew-smoke.hew
```

Expected `otool -L` output is limited to system paths under `/usr/lib/` and
`/System/Library/`. Any `/opt/homebrew/` or `/usr/local/opt/` entry is a
release blocker.

## Phase 5 — Candidate tag and publication order

Tag the qualified release-branch commit after its release PR merges into
`main`. Use a merge commit so that the candidate and its tag are reachable
from `main` and `git describe` resolves for later commits. Main can continue
receiving changes while the candidate is qualified; the published source stays
the exact source that passed the release gate and dry run.

Restore `release_sha` from the recorded, fully qualified candidate if using a
new shell, then check out that commit. Run these guards from its clean checkout
after the merge; they use only `main`, so the release branch may be deleted:

```bash
set -euo pipefail
: "${release_sha:?Set release_sha to the recorded fully qualified candidate SHA}"
[[ "$release_sha" =~ ^[0-9a-f]{40}$ ]]
test "$(git status --porcelain)" = ""
test "$(git rev-parse HEAD)" = "$release_sha"
release_tag="$(scripts/release-identity.sh)"
git fetch origin main
git merge-base --is-ancestor "$release_sha" origin/main
```

1. Confirm the recorded candidate satisfies the platform policy and required
   checks, including sanitizer evidence, packaging proof, required secrets and
   branch protection. Record accepted nonblocking failures and follow-up owners.
2. Create the signed tag and push it only after the preceding evidence is recorded:

   ```bash
   git tag -s "$release_tag" "$release_sha" -m "Hew $release_tag"
   git push origin "$release_tag"
   ```

3. The tag runs `.github/workflows/release.yml` (see "What happens on a `v*`
   tag"). Approve the `release` environment once when
   the run reaches it; everything else proceeds on its own. If a job fails,
   fix the cause and use **Re-run failed jobs**; npm and OCI content already
   published must match the producer artefacts before the job completes.
4. Verify npm with `npm view @hew-lang/wasm@<version> dist-tags version` and,
   from a scratch project that installs both packages, `npm audit signatures`
   (verified registry signatures and attestations). A prerelease must hold
   `next`, never `latest`.
5. Pin the candidate and cut over the banner in `hew.sh` and `hew.run` (see
   "Downstream repositories").
6. Rebuild Android from the tagged candidate and verify its artifact.

Do not tag until the recorded candidate satisfies the platform policy and
relevant release packaging proof. Resolve major supported-platform build/run
regressions and record any accepted nonblocking failures and their owners.
In particular, `gate-sanitizers` must have executed ASan successfully. Review the latest completed nightly run for its recorded revision
and scope. Current workflows do not execute TSan or Miri; before tagging,
record the coverage and release-acceptance decision for that missing evidence
(see [Sanitizer trust contract](#sanitizer-trust-contract)).

macOS release notes:

- ARM64 release builds run on `macos-15`
- `MACOSX_DEPLOYMENT_TARGET=13.0` is exported in the release workflow so the
  shipped binaries remain compatible with macOS 13+
- Tag releases require all of:
  - `APPLE_CERTIFICATE_P12`
  - `APPLE_CERTIFICATE_PASSWORD`
  - `APPLE_API_KEY_P8`
  - `APPLE_API_KEY_ID`
  - `APPLE_API_ISSUER_ID`
- If any required Apple secret is missing on a tag release, the macOS job must fail

## Phase 6 — Post-release verification

- [ ] The GitHub Release has the five current platform archives, the WASI library
      archive, both npm tarballs, the checksum manifest and, for a final
      release, the Linux packages; `gh attestation verify <asset> --repo
hew-lang/hew` passes for a downloaded archive
- [ ] Download and smoke-test at least one platform archive
- [ ] `docker run --rm ghcr.io/hew-lang/hew:<version> version` reports the tag
- [ ] Homebrew formula updated: `brew install hew-lang/hew/hew`
- [ ] docs.hew.sh shows the new release's standard library. Once the run's
      artefacts have expired (90 days), redeploy from the tagged checkout with
      `make release && make publish-docs` and run the `wrangler pages deploy`
      command it prints
- [ ] VS Code extension tagged and published from vscode-hew
- [ ] Author blog post at `hew-lang/hew.sh/src/content/blog/<YYYY>/<MM>/release-v<XYZ>.md` — required for any release with breaking changes; recommended for all minor releases.
- [ ] Verify the live `hew --version` on a freshly-installed binary matches the tagged version.
- [ ] Open the next planned development version on main in a separate PR. After
      v0.6.1, set the base to `0.6.2`; after v0.6.2, set it to `0.6.3`. Do not
      alter the qualified release commit, move its tag, or change edition 2026.

From a clean branch based on current main, run the existing bump machinery:

```bash
# Example closeout after publishing v0.6.2. Store the base, not a -dev suffix.
scripts/bump-version.sh 0.6.3
make test-build-version baselines-check
make lint

git diff --stat
# Review and commit all version identities, lockfiles and regenerated fixtures.
```

Keep `CHANGELOG.md`'s `[Unreleased]` section for the new development cycle;
do not create release notes or a release tag for this bump. A build from the
resulting commit reports `0.6.3-dev.X+<commit>`, with `X` counted from v0.6.2
when that tag and its history are present. Merge the bump PR as part of release
closeout, rather than leaving main labelled with the version just shipped.

## Downstream grammar sync

Any PR that modifies `docs/syntax-data.json` must also run the downstream sync
before the PR merges, or immediately after on a follow-up branch:

```bash
scripts/sync-downstream.sh --check   # dry-run: confirm drift matches expectations
scripts/sync-downstream.sh --commit  # apply and commit in each sibling repo
```

Verify the resulting commits in `tree-sitter-hew`, `vscode-hew`, `vim-hew`,
`hew.sh`, and `hew.run` are merged before tagging the release.

If the sibling-repo commits cannot land synchronously with the hew PR, open
PRs in those repos as a follow-up immediately. Unsynced downstream grammars
cause keyword-highlighting gaps that are invisible from this repo's CI.

## Known gaps (tracked)

### Sanitizer trust contract

The release branch gate runs `make asan` directly. A missing, skipped, or red
ASan execution therefore fails the job without an intermediate result file or
waiver parser.

The current [nightly sanitizer workflow](../.github/workflows/nightly-sanitizers.yml)
executes `make asan`, six partitions of `make core-safety`, the
`make test-host-safety` and `make test-extern-bytes-safety` integrations, and
`make fuzz-smoke`. Every job blocks the nightly result. Record the reviewed
run's revision and job outcomes; a successful run is evidence only for that
revision and scope.

Current workflows contain no TSan or Miri jobs, so current CI evidence for
either is unavailable. `make tsan` and `make miri` remain local entry points,
not recurring CI proof. Before release, review the missing race, aliasing and
pointer-provenance coverage and record the required coverage and
release-acceptance decision. A green ASan or nightly result does not supply
that missing evidence or establish safety sign-off.

- **The release-branch ASan gate is only as broad as `make asan`.** Today
  that command runs the `hew-runtime --lib` ASan suite. It does not by itself
  prove integration-only free sites, thread-reachable handle leaks, or every
  packaged binary path are covered. The separate nightly generated-code/runtime
  partitions and host/extern-byte safety integrations add coverage without
  expanding the release-branch job's scope. Expanding `make asan` to integration
  binaries is a tracked follow-on; once it grows, the release gate inherits
  that coverage automatically.

- **Miri: current CI evidence unavailable.** The local `make miri` target
  covers a curated pure-Rust unsafe subset. FFI, syscall, socket and subprocess
  paths remain outside its model; review the toolchain and scope of any new
  results before using them as release evidence.

- **Windows codegen**: release-gate and tag workflows provision LLVM 22, build
  the release compiler and `hew.lib`, and execute a Rust-staticlib consumer
  through `hew build --link-lib`. Ordinary PR CI remains the faster workspace
  path; the release workflows are the platform artifact authority.
- **Release-gate sandbox parity**: native↔sandbox-VM parity is enforced per PR
  on Linux by `ci.yml` with `make sandbox-parity`. The release gate does not
  rerun that Node/npm-backed harness across its platform matrix; rerun
  `make sandbox-parity` locally before tagging when cutting a release candidate.
- **linux-aarch64**: The pre-tag release gate builds and tests on a native
  Ubuntu 24.04 arm runner; the tag workflow additionally runs packaged-archive
  and clean-room smoke checks.
- **FreeBSD**: x86_64 has a full pre-tag build/test lane; aarch64
  proves only the release compiler build and compile/run smoke under emulation.
  Its pre-tag lane does not build the LSP, observe tool or release library, or
  execute the Rust/compiled-Hew suites. The current tag workflow builds and
  requires only the x86_64 FreeBSD archive; no aarch64 archive job or required
  asset exists. Apply the platform policy to failures and track the missing
  aarch64 archive as a distribution gap rather than a shipped product. Cross-built
  aarch64 libraries do not prove a shipped archive. The x86_64 nightly remains
  additional early warning rather than the release authority.
- **Local Debian bookworm arm64 hosts**: `apt.llvm.org/bookworm` arm64 does not
  publish the LLVM 22 packages the release build uses. Validate linux-aarch64
  on Ubuntu 24.04 arm64 instead (CI `ubuntu-24.04-arm`, or an Ubuntu 24.04
  arm VM/container / remote host).
- **TSan (Rust runtime): current CI evidence unavailable.** The local
  `make tsan` target instruments the standard library, libtest and runtime
  together. It selects native runtime unit tests with `--no-default-features`
  by default; `TSAN_TEST_ARGS` and `TSAN_TEST_FILTER` select additional features,
  integration tests and name filters. It stops on a reported race and uses no
  default suppressions. Record the actual toolchain, target and executed scope;
  no current nightly TSan job is available to review.
- **WASM capability gaps**: In-memory pipes and cooperative timers execute on
  WASI. File-backed streams, native networking and other host facilities retain
  target-specific limits. Use the
  [WASM capability matrix](wasm-capability-matrix.md) for the current browser and
  WASI support table and its execution evidence.
